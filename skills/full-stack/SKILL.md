# Full Stack

اعمل كنقطة دخول واحدة للمهارات الأربع. نسّق تنفيذها حسب حاجة الطلب، وحافظ على عقود متسقة بين المعمارية والبيانات والخلفية والواجهات والتحقق. نفّذ العمل المطلوب فعليًا حتى التسليم؛ لا تكتفِ بخطة أو قائمة مهارات.

## حمّل المهارات المرتبطة

اقرأ [خريطة المهارات](references/skill-map.md) وحدّد مواقع المهارات من أسمائها الدقيقة. افتح SKILL.md لكل مهارة تحتاجها قبل تنفيذ مرحلتها، ثم المراجع المطلوبة منها. في مشروع متكامل حمّل الأربع؛ في إصلاح محدود حمّل المعنيّة فقط. قراءة اسم المهارة أو ذكره لا يعني تطبيق تعليماتها.

- `template-architecture`: بنية المشروع والقالب الفارغ وحدود الطبقات.
- `template-backend`: Domain وApplication وInfrastructure وAPI والبيانات والأمن.
- `template-frontend`: React وBlazor وعقود الاتصال والتنقل والعرض.
- `template-verification`: فحص المعمارية والاختبارات والبناء والنشر وأدلة التسليم.

استخدم القالب والسكربتات من موقع `template-architecture` الفعلي؛ لا تنسخ نسخة ثانية منها إلى هذه المهارة. لا تفترض وجود أداة برمجية باسم use_skill ولا أن المنصة تستدعي المهارات تلقائيًا: الربط يتم بتحميل تعليماتها وتطبيقها. لا تنشئ وكلاء إضافيين لمجرد استخدام هذه المهارة؛ التفويض يخضع لتعليمات الجلسة.

## 1. حدّد النطاق وافحص الموجود

1. حدّد هل الطلب مشروع جديد، قالب فارغ، إضافة ميزة، استبدال واجهات، إصلاح، أو مراجعة فقط. لا تحوّل طلب المراجعة إلى تعديل، ولا تملأ القالب الفارغ بوظائف منتج.
2. افحص المشروع المرفق وتعليمات AGENTS.md والأجزاء ذات الصلة وحالة التغييرات قبل الكتابة. احتفظ بعمل المستخدم والتصميم والمحتوى المعتمد.
3. استخرج الأدوار والصفحات والبيانات والتكاملات ومتطلبات اللغة والثيم من الطلب. استخدم القرارات الموجودة بدل إعادة السؤال. اسأل فقط عن نقص يمنع قرارًا جوهريًا، ونفّذ الأجزاء المستقلة المتاحة أولًا.
4. أنشئ خطة قصيرة عند تعدد المراحل. حدّد معيار قبول لكل ميزة وتتبع الإنجاز بالأدلة، لا بعدد الملفات.
5. استخدم المعمارية الحالية للمشروع القائم. إذا كان خارج منظومة Template، لا تستبدل تقنياته تلقائيًا؛ اعرض التعارض المحدد واتبع النطاق الذي طلبه المستخدم.

## 2. ثبّت المعمارية والعقود

طبّق `template-architecture` قبل التوليد أو إعادة الهيكلة. للقالب الجديد استخدم سكربت الإنشاء في وجهة جديدة فقط. للمشروع الموجود عدّل الملفات الحالية ولا تضع قالبًا ثانيًا داخله.

استخدم [عقد التكامل](references/integration-contract.md) لتحديد مسار API وطريقة HTTP وDTO والأخطاء والصلاحيات والملكية والصفحة المستهلكة. استخرج ما هو موجود أولًا، وحدّث الطرفين معًا عند تغيير العقد. لا تخترع endpoint أو بيانات اعتماد لتجاوز نقص فعلي.

احفظ القواعد الأساسية لمعمارية Template:
- خادم ASP.NET Core واحد للإنتاج؛ React داخل ClientApp وBlazor داخل Components.
- Domain مستقل؛ Application للعقود وحالات الاستخدام؛ Infrastructure للتنفيذ وSQL Server؛ Controllers رفيعة.
- لا تضف Express أو Firebase أو قاعدة بيانات داخل ClientApp.
- اربط بيانات العمل والدخول بواجهات حقيقية؛ لا تستبدلها بـmock أو localStorage. تفضيلات العرض غير الحساسة فقط يمكن تخزينها محليًا إذا سمح المشروع.
- حافظ على التصميم المعتمد، وإصدارات المشروع، ومواقع الملفات ما لم يتطلب الطلب تغييرها.

## 3. نفّذ ميزة متكاملة في كل مرة

استخدم `template-backend` لتطبيق الكيان وقواعده وحالة الاستخدام وواجهة التخزين وEF configuration والـmigration عند الحاجة وController وتسجيل الخدمات. طبّق صلاحيات الخادم وعزل المالك والتحقق من المدخلات.

مرّر العقد الفعلي إلى `template-frontend` واربط الصفحة والعمليات بنفس المسارات والـDTO والأخطاء. غطِّ التحميل والفراغ والفشل ونجاح الحفظ. وحّد الجلسة وCSRF وعقد المصادقة مع الخادم. لا تغيّر اسم حقل على طرف واحد.

تحقق من المسار كاملًا: تفاعل المستخدم → الطلب → حالة الاستخدام → التخزين → الاستجابة → تحديث العرض. افحص إعادة تحميل الصفحة واستمرار البيانات بعد اتصال جديد. أكمل الميزة الحالية قبل تعميمها على بقية الصفحات.

إذا تغير عقد أو صلاحية أثناء التنفيذ، حدّث الخلفية والواجهة والاختبار قبل اعتبار الميزة منجزة. إذا فشل الفحص، حدّد الطبقة المسؤولة، أصلحها ثم أعد الفحص المتأثر فقط.

## 4. أكمل التغطية المطلوبة

في استبدال الواجهات، احصر كل الصفحات والمكونات ومساراتها ثم تأكد من ربطها قبل إزالة النسخ القديمة غير المستخدمة. لا تكرر مجلدات components أو تحتفظ بواجهة قديمة داخل نسخة نهائية جديدة.

إذا طُلبت العربية والإنجليزية أو الوضعان الليلي والنهاري أو بوابات منفصلة، طبّقها على كامل النطاق المطلوب مع RTL/LTR والجوال والكمبيوتر وعزل الأدوار. لا تضف بوابات أو تصميمًا جديدًا من تلقاء نفسك.

إذا طُلبت seed data، اجعلها فعلية ومتسقة مع العلاقات وقابلة للتكرار دون تكرار السجلات، ومعطلة في الإنتاج افتراضيًا. إذا طلب OAuth أو مزود خارجي، نفّذ التكامل الصحيح وبيّن الإعداد المتبقي عند غياب بيانات الاعتماد؛ لا تعرض نجاحًا وهميًا.

## 5. تحقّق وسلّم

طبّق `template-verification` وفق المخاطر والتغييرات الفعلية. تحقق من TypeScript وReact build وبناء .NET والاختبارات والمعاملات وقاعدة SQL والنشر ومسارات SPA وBlazor بحسب النطاق والأدوات المتاحة.

لا تجعل فشل أداة واحدة يوقف إصلاحات مستقلة يمكن إتمامها؛ لكن لا تستبدل اختبار SQL بمحاكاة ثم تدّعي تحقق SQL. لا تعتبر الملف أو صفحة العرض وحدهما دليلًا على نجاح التكامل.

سلّم للمستخدم النتيجة والملفات أو المشروع المطلوبين مع وصف موجز لما تغيّر وما اختُبر وما بقي معطلًا وسبب ذلك. صنّف الأدلة إلى VERIFIED وNOT VERIFIED وBLOCKED BY ENVIRONMENT. لا تدّعِ اكتمال التشغيل أو المصادقة أو النشر دون دليل. إنشاء artifact محلي لا يساوي نشره خارجيًا؛ نفّذ النشر أو تعديل بيانات الإنتاج فقط إذا كان مأذونًا ضمن الطلب.
