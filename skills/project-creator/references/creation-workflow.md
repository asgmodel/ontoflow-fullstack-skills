# Creation lifecycle and recovery

## Ordering

Receive idea → prepare brief → create/verify ChatGPT project → create/verify GitHub repository → initialize appropriate project records → create/verify task chats → dispatch ready work → publish linked register.

Keep this ordering where practical. If one service is blocked, prepare independent work on the other within the user's scope. Mark the blocked resource explicitly; do not claim the whole setup is complete. Resume by reconciling saved identities and uncertain operations.

## Operation records

Before mutation record an operation key, resource kind, intended owner/name, current state and related task. Use states `planned`, `attempting`, `uncertain`, `verified`, `failed`, `blocked`. Retain observed identity/URL and verification evidence separately. A timeout after clicking Create is `uncertain`, not permission to create again.

On resume inspect the intended exact project/repository/chat through the available service interface. Reuse the verified result. Resolve genuine ambiguity with the user rather than overwriting an unrelated match. Do not delete/rename resources as speculative cleanup.

## ChatGPT project controls

Read current browser guidance. Prefer exposed page actions; fetch current tool descriptions per turn/document and never persist opaque tool suffixes. For fallback UI use inspected semantic controls or fresh accessibility indices. Reinspect after transitions and verify saved identities rather than spinners/provisional local URLs.

A browser tab is not a ChatGPT project. A chat visible beside a project in the sidebar is not membership evidence. Use the project's own view or a direct membership indicator. If a chat was created outside, move it through the observed supported control and verify the target.

Follow secure authentication, device verification and site-blocking guidance. An expired/new challenge requires the exact live number/method. Do not inspect/print tokens, cookies or password values. Stop at an actual blocker and retain useful setup.

## Boundaries

A user request to create a project/repo authorizes the necessary ordinary setup within the stated scope; do not introduce repeated final approval turns for routine in-scope choices. Follow actual higher-priority rules for security-sensitive access, public exposure, legal terms and consequential actions. Creation does not authorize deployments, collaborator invitations, paid resources or production data changes.

Do not read unrelated private projects/chats while searching for the target. Preserve existing user source and product decisions.
